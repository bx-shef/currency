# Новый агент

Операция: сделать фоновую задачу, которая не начинает работу, когда её уже
делает другой экземпляр, и не встаёт намертво из-за того, что предыдущий
запуск был убит.

## 1. Класс задачи

Агент Битрикса — статический метод, возвращающий строку своего следующего
вызова. Держите в нём только обвязку, работу выносите в обычный класс.

```php
namespace Shef\Demo\Agent;

use Shef\Options\Main\TempFile\Pid;

final class Import
{
    /** Имя группы блокировок: одна задача — одна группа. */
    private const GROUP = 'shef.demo.import';

    public static function run(): string
    {
        $self = '\\'.static::class.'::run();';

        $lock = new Pid(self::GROUP);

        // add() создаёт СВОЙ файл и попутно убирает блокировки мёртвых
        // процессов. false означает «не смог записать файл».
        if(!$lock->add())
        {
            return $self;
        }

        try
        {
            // «Занято ли» решается по каталогу группы, а не одним вызовом:
            // после add() там остались только ЖИВЫЕ блокировки — своя и
            // чужие. Больше одной — работает кто-то ещё.
            if(count(glob(Pid::getBasePath(self::GROUP).'/*.lock')) > 1)
            {
                return $self;
            }

            // ... работа
        }
        finally
        {
            // finally обязателен: исключение не должно оставить блокировку
            $lock->remove();
        }

        return $self;
    }
}
```

**Почему не `isExist()`.** Напрашивается «спросить, занято ли» одним вызовом,
и такого вызова у класса нет. `isExist()` проверяет **свой** файл, а имя файла
содержит pid процесса — у второго экземпляра он другой, так что `isExist()`
вернёт `false`, `add()` вернёт `true`, и второй процесс спокойно пойдёт
работать рядом с первым. `add()` чужие живые блокировки тоже не проверяет.
Занятость группы приходится выводить из каталога — это и делает `glob()` выше.

**Строгой взаимной блокировки это не даёт.** Два процесса, стартовавшие
одновременно, могут оба создать файл, оба увидеть двойку и оба уйти —
пропущенный запуск вместо двойной работы. Для задач, где пропуск недопустим,
берите блокировку СУБД (`GET_LOCK`, advisory lock), а `Pid` оставьте как
видимый след «кто сейчас работает».

**`finally` здесь не украшение.** Упадёт работа — без него блокировка
останется, и группа будет считаться занятой до тех пор, пока следующий запуск
не опознает процесс мёртвым.

## 2. Что даёт `Pid`

* имя файла содержит pid процесса, поэтому два процесса одной группы получают
  разные файлы, а один и тот же процесс узнаёт свой по имени;
* `add()` сам убирает блокировки **мёртвых** процессов — упавший по `-9` или
  по фатальной ошибке предыдущий запуск не держит группу вечно. Живые и те,
  про которые выяснить нечем, не трогаются;
* `Pid::removeByGroup(GROUP)` останавливает всю группу — но **по умолчанию
  шлёт процессам SIGTERM**. Нужно только убрать файлы, никого не трогая —
  передавайте `0` вторым аргументом;
* файл живёт до `remove()`: концом скрипта он сам не удаляется.

Запускаемый пример со всеми случаями — [examples/pid.php](https://github.com/bx-shef/options/blob/main/examples/pid.php), гоняется и на
заглушках, и на живом портале.

## 3. От чьего имени работает агент

Агент выполняется **без пользователя**, и это не недосмотр: ядро перед вызовом
агента само обнуляет `$USER` (`main/classes/general/agent.php`, «global $USER
should not be available here»). Поле `USER_ID` у агента — только подпись в
списке, при запуске ядро его не читает. Поэтому не «становитесь» пользователем,
а **называйте его явно в каждом вызове**, где он нужен.

**Действует система** (дела, комментарии, записи CRM от модуля). ID —
служебный пользователь из настроек shef.options, проверку прав «текущего»
выключаете там, где агент действует от имени системы:

```php
$systemUserId = \Shef\Options\Main\Constants::getSystemUserId();

// Дело CRM: автор — служебный, исполнитель — менеджер, права «текущего» не проверять
$todo = new \Bitrix\Crm\Activity\Entity\ToDo($owner, new \Bitrix\Crm\Activity\Provider\ToDo\ToDo());
$todo->setCheckPermissions(false)
    ->setAuthorId($systemUserId)
    ->setResponsibleId($managerId)
    ->setSubject('Перезвонить клиенту');
$result = $todo->save();

// Запись CRM фабрикой: пользователь — в контексте операции, а не в сессии
$context = (new \Bitrix\Crm\Service\Context())->setUserId($systemUserId);
$operation = $factory->getUpdateOperation($item, $context)->disableCheckAccess();
$result = $operation->launch();
```

**Действует от имени сотрудника** (агент выполняет то, что поставил человек) —
права проверяете явно по его ID, до действия, а не подменой:

```php
$permissions = \Bitrix\Crm\Service\Container::getInstance()->getUserPermissions($userId);
if(!$permissions->checkReadPermissions($entityTypeId, $id))
{
    return; // сотруднику нельзя — агенту тоже
}
```

Пустая или испорченная настройка «служебный пользователь» даёт умолчание —
пользователя с ID 1, обычно администратора. Записи модуля тогда будут от его
имени; если это недопустимо, сверяйте ID в начале `run()` и не работайте с 1.

**`FixUser` — не для новых агентов.** Трейт
`\Shef\Options\TraitList\Security\FixUser` подменяет пользователя через
`CUser::Authorize()`, то есть записью в сессию. На хите посетителя это его
сессия, и сбой посреди работы оставлял посетителя (даже анонима) под чужим
именем — эскалация прав, замер в
[bx-shef/options#48](https://github.com/bx-shef/options/issues/48). С shef.options
3.4.0 `initUser()` вне процесса cron (PHP CLI) бросает `\LogicException`. Он
остаётся только для API ядра, которое смотрит строго на «текущего» и не
принимает пользователя параметром (поиск «Базы знаний» `note`): тогда — только
с cron (`BX_CRONTAB_SUPPORT`), в `try` / `finally` с `closeUser()`, а на хите
работа пропускается с понятным сообщением.

## 4. Регистрация

В `DoInstall()` установщика:

```php
\CAgent::AddAgent(
    '\\Shef\\Demo\\Agent\\Import::run();',
    'shef.demo',      // модуль: удалится вместе с ним
    'N',              // $period, см. ниже
    3600              // интервал, секунд
);
```

`$period` решает, как считается интервал: строго по расписанию или от конца
прошлого запуска. Для долгой задачи разница принципиальна — прогон длиннее
интервала при одном значении даёт очередь запусков, при другом нет. Какое
значение нужно вам, проверьте на стенде: запустите задачу, которая работает
дольше интервала, и посмотрите в списке агентов время следующего вызова.

Модуль во втором аргументе обязателен — иначе при удалении модуля агент
останется в базе и будет падать с «class not found» каждый запуск.

**В `DoUninstall()` не обращайтесь к классам своего модуля.** `Import::GROUP`,
`PriceLog::GROUP` и подобное падает с `Class not found`: на момент удаления
автозагрузка вашего модуля уже не работает. Имя группы придётся повторить —
литералом или константой самого `install/index.php`. Дублирование тут
осознанное: один литерал в двух файлах дешевле, чем падение установщика.

```php
// install/index.php
private const LOCK_GROUP = 'shef.demo.import';   // то же, что в классе агента

public function DoUninstall(): void
{
    \CAgent::RemoveModuleAgents('shef.demo');

    // shef.options — чужой модуль, он остаётся на портале; но подключить его
    // надо явно: автоматически в установщике он не загружен.
    //
    // try/catch обязателен, и не из вежливости: DoUninstall() не имеет права
    // оборваться из-за вспомогательного вызова в чужую библиотеку. Оборвётся —
    // файлы модуля уже сняты, а регистрация, агенты и обработчики остались, и
    // доудалить штатно нечем: install/index.php, которым удаляют, тоже снят.
    // Именно так и случилось на портале: shef.options 3.0.15 бросал из
    // removeByGroup(), если каталога группы ещё не было.
    if(\Bitrix\Main\Loader::includeModule('shef.options'))
    {
        try
        {
            $result = \Shef\Options\Main\TempFile\Pid::removeByGroup(self::LOCK_GROUP, 0);
            if($result->isSuccess())
            {
                // rmdir, а не deleteDirectory: снимет только ПУСТОЙ каталог.
                // Ошибка в имени группы не унесёт чужие замки.
                @rmdir(\Shef\Options\Main\TempFile\Pid::getBasePath(self::LOCK_GROUP));
            }
        }
        catch(\Throwable $exception)
        {
            // Замки остались — это задержка, а не поломка. Удаление идёт дальше.
        }
    }

    $this->UnInstallFiles();
    $this->UnInstallDB();
}
```

Без уборки после снятия модуля во временном каталоге портала остаются замки.

Путь к ним **спрашивают у `Pid`, а не пишут строкой**, и на то две причины.

Во-первых, каталог не в `/bitrix/tmp/`: `Pid` кладёт файлы во временный
каталог портала — `upload/tmp`, а если задана `BX_TEMPORARY_FILES_DIRECTORY`,
то куда укажет она, хоть за пределы `DOCUMENT_ROOT`. `DeleteDirFilesEx()`
принимает путь от корня сайта и до такого каталога просто не дотянется.

Во-вторых, каталог **общий**. `Pid::getBasePath()` собирает путь как
`<временный каталог>/shef.options/<группа>` — `shef.options` там всегда,
это идентификатор библиотеки, а не вашего модуля.

Если удаление уже оборвалось на середине — файлы модуля сняты, а сам он
числится установленным, — штатно его не доудалить: `install/index.php`
тоже снят. Как выбраться — в
[docs/portal-check.md, «Если удаление уже обрывалось на середине»](https://github.com/bx-shef/options/blob/main/docs/portal-check.md#если-удаление-уже-обрывалось-на-середине). Значит удалять можно
**только свою группу** и только пустой каталог — поэтому `@rmdir()` после
успешного `removeByGroup()`, а не `Directory::deleteDirectory()`: при пустом
`LOCK_GROUP` путь `getBasePath('')` — это каталог библиотеки целиком, и
рекурсивное удаление стёрло бы его. Снесёте каталог уровнем выше — заберёте с собой
замки всех остальных модулей портала, включая живые.

Второй аргумент `removeByGroup()` равен нулю намеренно: по умолчанию метод
шлёт процессам из файлов группы `SIGTERM`, а при удалении модуля стрелять по
чужим процессам незачем.

Уборка **не обязана получиться**, и удаление модуля от неё не зависит. С
`shef.options` 3.0.16+ `removeByGroup()` исключений не бросает — отказы
складываются в `Result`, — но `try/catch` в `DoUninstall()` всё равно нужен:
версию библиотеки на портале вы не выбираете, она обновляется отдельно от
вашего модуля.

## 5. Cron вместо агента

Агенты запускаются хитами посетителей: на портале без трафика задача не
выполнится. Для тяжёлых и регулярных задач берите cron и отдельный
cli-скрипт — блокировка через `Pid` там нужна ровно так же и работает
одинаково.

## 6. Проверка

1. Запустить задачу руками, во время работы запустить второй раз — второй
   должен уйти, не начав работу.
2. Убить процесс по `-9`, запустить снова — **должен стартовать**: `add()`
   уберёт мёртвую блокировку. Если не стартовал, блокировка считается живой,
   и это надо разбирать, а не удалять файл руками.
3. Посмотреть каталог группы: после нормального завершения файлов не осталось.
4. Проверить, что агент не трогает `$USER` и сессию: записи созданы от служебного пользователя, у открытой вкладки портала пользователь не сменился.
5. **Снять модуль, у которого агент ни разу не отработал.** Удаление обязано
   дойти до конца: модуль снят с регистрации, агентов не осталось, замки
   чужих групп на месте. Шаг появился не на пустом месте — именно здесь
   удаление и обрывалось, и нашёл это клиентский портал, а не тест.
